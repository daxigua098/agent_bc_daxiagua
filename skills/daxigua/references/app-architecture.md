# 应用与后台架构

## 账号与登录

- 账号形态：游客（可升级）、手机/邮箱、第三方登录，升级与绑定要保证资产不丢。
- 多端同步：同一账号在多设备登录时的会话与余额一致性。
- 风险控制：设备指纹、异地登录提醒、敏感操作二次验证。
- 登录模板类项目要预留：品牌化配置（Logo/主题/文案）、多语言多币种、以及不同市场的准入开关。

## 与游戏厂商接入

两条主链：seamless wallet（实时调平台接口）与 transfer wallet（转账钱包）。

工程要点：

- 幂等：所有扣款、派彩、转账接口都要有幂等键与唯一约束。
- 超时与补偿：接口超时先挂起，用任务查证，绝对不做「超时后本地自行判定输赢」。
- 对账：厂商报单与本地注单双向对账，差异清单自动生成。
- 多厂商统一抽象：同一套内部模型承载不同厂商字段，避免玩法逻辑散落各处。

## 实时数据

- 赔率推送用 WebSocket/SSE，设计上要有快照 + 增量 + 顺序号，支持断线重连补数据。
- 推送延迟与封盘判定：以服务端时间为准，客户端时间只做展示。

## 订单与结算服务

- 注单状态机集中实现，其他模块只发事件、不改状态。
- 结算链路推荐事件驱动 + 可重放，便于事后审计与重算。
- 金额计算集中在一处（统一精度与舍入策略），业务模块不得各自实现一套。

## 支付

入金通道选择、成功率监控、回调幂等、限额与风控联动、拒付与争议处理；出金要有审核队列与进度可查。支付手续费口径要写进净利计算。

## 活动与促销

规则引擎化：领取条件、流水要求、有效期、叠加规则、上限。防刷是第一优先级，活动上线前先跑一遍刷量路径。

## 运营后台

通常需要：会员管理、注单查询与重算、钱包与流水查询、代理与佣金结算、报表（总投注、有效投注、GGR、NGR、返水、代理分成）、风控工作台、内容与公告、操作审计。

报表口径必须先定再开发。同一个「业绩」在不同口径下差额可能非常大，改口径等于重做报表。

## 非功能要求

- 时间：统一 UTC 存储，展示按玩家时区；跨天以明确时区切分。
- 精度：金额用整数最小单位或高精度十进制。
- 审计：资金与状态变更全部留痕，不可篡改。
- 发布：灰度、回滚预案，风控与结算相关改动需有对账验证步骤。
- ID 命名统一（bet ID、round ID、event ID、member ID），跨系统可追溯。
