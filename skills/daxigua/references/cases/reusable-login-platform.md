# 案例：可复用登录平台（客户端 + 服务端）

来源：真实交付项目「登录模版 / 可复用登录平台 V2」，2026-09 在 Windows 客户端 + Linux 服务端跑通并打包成单文件 EXE。本文所有域名、IP、账号、app_key 已脱敏。

## 结论先行

- 多平台登录的复用点在「通用流程 + 平台适配器」，不在复制整套代码。
- 客户端与服务端必须是两个独立项目包：服务端不做平台网页登录，客户端不直连服务器数据库。
- 会话必须用业务接口验证过才算有效，只看 Cookie 存在不算登录成功。
- 凭据和会话都不落明文：账号密码进系统凭据库，会话用 DPAPI + AES-GCM 加密落盘。
- 验证码、短信、二次认证、风控一律人工接管，不做任何绕过。

## 1. 职责边界

| 端 | 负责 | 不负责 |
| --- | --- | --- |
| 服务端 | 数据采集与入库、账户认证、授权与有效期、客户端校验、心跳、审计 | 平台网页登录 |
| 客户端 | 首次授权申请、平台登录、会话捕获与加密、数据读取、自动重连、多窗口 | 直连服务器数据库 |

## 2. 客户端多窗口流程

```text
启动与自检
  -> 首次授权窗口（读机器码、读本机 IP、输入用户名、提交人工审批）
  -> 客户端账户登录（密码校验 + 权限/有效期）
  -> 平台网页登录（QtWebEngine，自动填充账号密码）
  -> 人工认证窗口（出现短信/二次认证/风控时按需弹出）
  -> 主窗口（登录窗口隐藏或销毁）
```

主窗口必须保留「重新登录」与「自动重连」，掉线后不能只能靠重启软件恢复。主窗口按页面拆分，不把所有功能塞进一个面板：运行概览 / 数据同步 / 会话中心 / 账户与授权 / 任务与日志 / 设置与诊断。

## 3. 平台适配器

适配器只做两件事：**怎么登录**、**怎么判断登录成功**。通用能力放在公共 JS 工具库，平台差异放在各自的适配器里。

三类适配器覆盖了绝大多数站点：

- `generic_web`：找页面上第一个账号框、密码框和提交按钮；识别不到就明确交人工，不硬猜。
- GraphQL 品牌适配器：直接向后端登录接口发 mutation，拿到 token 后按该品牌的前端约定写入 localStorage 的 userInfo key，再跳转首页。
- React + 验证码品牌适配器：填表 → 点登录 → 用户在页面里人工完成验证码 → 轮询检测前端状态对象。

登录成功判定不要只看 URL，也不要只看密码框消失（SPA 路由不刷新会误判）。可靠做法是组合判断：URL 路径 + 前端状态对象 + token 长度。

JS 注入的四个通用工具函数是这套方案的复用重点：

1. 等待元素出现且可见（轮询 + 超时）
2. 写入输入框（用原生 setter 赋值，再派发 input / change / keyup / blur 事件）
3. 按可见文本点按钮
4. 读 localStorage / sessionStorage 并解析嵌套状态

只改 `el.value` 不派发事件，React / Vue / Angular 的表单不会更新状态，这是最常见的失败原因。

## 4. 会话捕获、验证与生命周期

捕获顺序：Cookie → localStorage / sessionStorage → 页面内存 token → 网络响应里的 Authorization。

验证方式：拿捕获到的会话去访问真实的业务地址（个人信息页、开奖数据接口），只有返回结构符合预期才标记有效。

保存方式：

```text
SessionVault
  -> AES-256-GCM（每次保存独立随机 Nonce）
  -> 密钥由 Windows DPAPI 按当前用户范围保护
  -> 写入 SQLite 或加密会话文件
```

生命周期状态要显式建模：未创建 → 登录中 → 已捕获 → 已验证 → 已加密保存 → 即将过期 → 刷新中 → 有效 → 过期 → 需重新登录。

刷新失败要有明确降级（提示重新登录），不要静默高频重试，那会把会话重试成风控事件。

## 5. 客户端授权体系

字段设计：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 用户名 | 是 | 默认授权校验字段 |
| 密码 | 是 | 服务端 Argon2id 哈希存储 |
| 机器码 | 否 | 可选的设备绑定条件 |
| IP 地址 | 否 | 可选来源条件 |
| 有效期起止 | 是 | 支持自动填充当前日期 |
| 期限类型 | 是 | 1 天 / 3 天 / 1 周 / 1 个月 / 3 个月 / 自定义 |
| 最大设备数 | 是 | 控制同一账号可绑定的机器数量 |

默认策略是**只验证用户名 + 有效期**，机器码和 IP 是按需打开的可选项 —— 一刀切绑死机器码会让正常换机、换网络全变成人工工单。

校验顺序（短路返回，顺序不能乱）：

```text
账户状态(active) -> 用户名 -> 密码 -> 有效期 -> 机器码 -> IP -> 设备名额
```

返回状态码要足够细，客户端才能给出可操作的提示：

```text
AUTHORIZED / PENDING_APPROVAL / DENIED / EXPIRED / NOT_STARTED
MACHINE_MISMATCH / IP_MISMATCH / USER_NOT_FOUND / USER_DISABLED
INVALID_CREDENTIALS / PASSWORD_NOT_SET
```

首次使用走人工审批流：客户端提交（用户名 + 机器码 + IP + 版本）→ 服务端记为 pending → 管理员审批并选择期限 → 服务端自动算 `valid_from / valid_to` 并绑定设备 → 客户端转为 AUTHORIZED。

两个时间字段必须分开：`added_at` 是管理员创建用户的日期，`first_activated_at` 是客户端首次授权成功的日期。合并成一个字段后，运营永远说不清"这个用户到底用没用过"。

## 6. 数据采集与刷新

```text
定时调度
  -> 请求主接口，失败自动切备用接口
  -> 解析 -> 校验 -> 标准化字段
  -> 按唯一约束（source_code + source_time）幂等入库
  -> 更新内存实时状态
  -> 写采集运行记录与审计日志
```

关键设计：

- **实时与历史分离**：实时列表读内存，历史查数据库。数据库只追加，不做删除。
- **保留原始响应**：`raw_payload` 存原始报文，标准化字段另存，出争议时可回溯。
- **增量同步**：客户端带 `version` 或 `ETag` 请求，内容未变返回 304；每条记录带 `content_hash`。
- **失败不覆盖**：网络失败走指数退避，绝不用空数据覆盖已有有效数据。
- **同一数据源同一时刻只跑一个采集任务**，用锁控制。

界面上的读秒（例如 60 秒倒计时）只更新数字控件，不整窗刷新 —— 整窗刷新会打断用户操作并造成闪烁。

## 7. 期号与号码派生（本项目实测规则）

```text
期号  = YYYYMMDD + (Hour * 60 + Minute + 1)，分钟序号补足 4 位
        例：2016-11-21 18:17:00 -> 18*60+17+1 = 1098 -> 201611211098
号码  = 各位数字求和取个位 + 原始数值后四位
        例：233192404 -> 2+3+3+1+9+2+4+0+4 = 28 -> 28 mod 10 = 8 -> 后四位 2404 -> 82404
```

派生字段在服务端入库时算好并落库，客户端不重新计算 —— 两端各算一次，迟早会因为时区或边界条件对不上。

## 8. UI 主题系统

五套 UI 是**同一软件的五个可切换主题**，不是五个独立程序。主题注册在配置文件里，默认主题 + 用户可切换，切换不重启，配置损坏自动回退默认主题。

主题只改颜色、背景、圆角、阴影、字级和动效，不改布局结构与权限逻辑。把"换皮"和"改功能"混在一起，后面每加一套主题都要回归一次功能。

## 9. 打包与发布

Python + PySide6 + QtWebEngine 可以打成单文件 EXE（PyInstaller），可选再用 Inno Setup 做安装包与卸载入口。用户不需要装 Python、不需要看到命令行窗口。

QtWebEngine 会显著增大体积（本项目单文件约 240MB），这是内置浏览器内核的正常成本，不要为了体积砍掉内置浏览器能力 —— 登录和人工认证都依赖它。

## 10. 部署（Windows → Linux + systemd）

```text
ssh 探测连通
  -> scp 上传更新包
  -> 服务器解压到临时目录
  -> 备份现有部署目录（带时间戳）
  -> 停服务 - 覆盖 - 启动服务
  -> 验证 /health 与业务接口字段
```

三条实际踩过的坑：

1. Windows OpenSSH 的 askpass 辅助程序路径含中文时会报 `CreateProcessW failed error:2`，必须放到纯 ASCII 路径（例如 `%TEMP%` 下的随机目录）。
2. 密码方式登录要把密码写临时文件，脚本必须用 `finally` 保证成功失败都清理。
3. 只验证 `/health` 会漏掉"服务起来了但跑的还是旧代码"。要验证一个业务接口的**新增字段**（例如返回里是否出现新字段），才能确认新版本真的生效。

另外把 `known_hosts` 写在工作区内而不是用户目录，避免污染开发机全局配置。

## 11. 安全红线

- 明文凭据不写入任何交付文档、代码、日志和截图；项目交接时提醒轮换已暴露过的密码。
- 日志对 `password`、`token`、`cookie`、`authorization` 自动脱敏。
- 退出时清理内存中的密码、Token 和明文会话。
- 不绕过验证码、短信、二次认证与平台风控；出现这类验证就切人工接管窗口。
- 服务端接口不返回明文密码，也不返回密码哈希，只返回"已设置 / 未设置"。
- 保留审计：授权、登录、采集、权限与系统操作全部留痕，审计表只读。

## 12. 复用到新项目时的检查清单

- 先确认目标平台的登录方式属于哪一类（表单 / 后端接口 / 混合 + 验证码），再决定写通用适配器还是品牌适配器。
- 会话有效性必须能用业务接口自证。
- 授权策略默认从宽（用户名 + 有效期），机器码和 IP 按需开启。
- 采集、去重、增量同步三件事各自有明确口径。
- 打包、部署、回滚三条路径在上线前都实际跑过一次。
